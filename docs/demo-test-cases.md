# Demo test cases

These cases cover the five assignment control groups. Run the automated commands recorded in [TODO.md](TODO.md); the UI suite needs a real desktop display because AssertJ Swing uses AWT Robot. For demo-account smoke tests, use the prepared distribution's credentials from the operator-only file outside the checkout. `test-distribution` works on a disposable package copy so that registration, purchases, and failed-login test data never reach the delivered database.

| Control Group | Test Scenario | Expected Outcome | Recorded Evidence |
| --- | --- | --- | --- |
| Authentication | Register a new user through the public form, then sign in. Inspect login, registration, and confirmation password controls. Submit an incorrect credential for a valid username; then submit five consecutive failures for a separate account. | Registration creates a Client account with a salted PBKDF2 hash. Password controls are masked. Invalid login uses one generic message. The account remains enabled after failures 1–4 and changes to Role 1 exactly on failure 5. | Pass: A behavior suite covers registration, hash format, generic responses, exact lockout boundary, and audit-write rollback; Swing UI suite covers registration, login masking, generic failure text, and exact five-attempt boundary. |
| Authorization | Sign in as each prepared Client, Staff, Manager, and Admin. Attempt a Client product mutation directly and inspect the Client product screen. Check that Manager can read all purchase history, Staff/Manager can manage products, Client can purchase/read own history, and only Admin can manage users/read audit records. | Each role enters only its corresponding home panel. Disallowed direct calls return denied, forbidden controls are hidden, and protected records are not returned. Role 1 and missing/stale actors receive no protected access. | Pass: A and B direct-provider suites cover role matrices and denied calls; Swing suite covers all four role routes, hidden Client product mutation controls, denied direct product mutation, and Admin audit search/show-all. |
| Data Validation | Try malformed/overlong usernames, weak passwords and lengths outside 8–64, invalid role values, signed or oversized stock/quantity, malformed/overprecision prices, overlong product/history/audit search text, and SQL-shaped filters. | Each invalid input is rejected as entered; no sanitization or partial state change occurs. Numeric ranges and field lengths are enforced. SQL-shaped values stay data and do not change query results. Validation rejections are audited when the required provider is available. | Pass: A suite reports 260 assertions across account/password/role/input boundaries; B suite covers product, purchase, and history boundaries and injection-shaped filters. |
| Error Handling | Force missing/unavailable storage and required audit failures during login, registration, account administration, product mutation, and purchase confirmation. Observe user-facing errors and session/navigation state. | The app returns a generic error, creates no session or partial mutation, and leaves or returns the user to an unprivileged Login state when a provider is unavailable. Required audit-write failure fails the associated action closed. | Pass: A/B provider suites test actual SQLite and injected audit/storage failures, transaction rollback, generic outcomes, and safe fallback; UI registration/login/purchase paths run on the production providers. |
| Logging | Produce successful/failed authentication, invalid-input, denied-access, product, purchase, and account-administration events. As Admin, search audit text/event filters and show all. Repeat audit search as Client and with no access provider. Inspect timestamps, credential exclusion, and retained rows. | Events have timestamps and contain no submitted passwords. Only current Role 5 can read/search audit records. Denials return no rows. Audit review is read-only; no action permanently deletes rows. A required audit write failure blocks or rolls back its operation. | Pass: A/B provider suites verify persistent rows, filters, access denial, transactional audit behavior, and repeatable initialization; Swing suite reviews actual Admin audit rows and filters. The prepared delivered DB begins with four hashed demo accounts, two products, two seeder-generated audit rows, and no purchase/history test rows. |

## Demo database and operator data

`prepare-demo-database` refuses to overwrite an existing target. The tracked distribution contains one Admin, Manager, Staff, and Client account; the database contains hashes only. The seeder writes generated passwords to a file selected outside the project checkout. That operator-only file is not tracked. The package smoke suite mutates a copy of `database.db`, not the delivered copy.
