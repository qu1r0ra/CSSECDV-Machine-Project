# Demo test cases

Status: These cases combine Bundle B [issue #6](https://github.com/qu1r0ra/CSSECDV-Machine-Project/issues/6) with shared audit behavior from [issue #16](https://github.com/qu1r0ra/CSSECDV-Machine-Project/issues/16). Temporary SQLite and controlled audit-provider checks cover the service seams. Interactive Swing search and full application walkthrough remain under [issue #17](https://github.com/qu1r0ra/CSSECDV-Machine-Project/issues/17); this is not yet the complete project demo plan.

| Control Group | Test Scenario | Expected Outcome |
| --- | --- | --- |
| Authentication | Open a B operation without an authenticated actor, then repeat with a Disabled (Role 1) account. | Every operation is denied and protected data is not returned. Current service checks use injected identity/session providers; verify the real A/C session behavior after integration. |
| Authorization | Attempt product management as Client and purchase as Staff; read history as Client and Manager. | Client cannot manage products; Staff cannot purchase or read history; a Client sees only the current account's purchases; a Manager can view all purchase and legacy rows. Admin and Disabled have no B privileges. |
| Data Validation | Submit names with spaces, signed stock, stock above 1,000,000, prices with excess precision/grouping/exponent notation, quantity above 1,000,000, and invalid history searches. | Each value is rejected unchanged, no partial mutation occurs, and invalid values produce timestamped audit rows. |
| Error Handling | Force the audit writer to fail during product creation and purchase confirmation. | The UI receives a generic failure; the transaction leaves no product/purchase snapshot and purchase stock remains unchanged. An unrecoverable provider/storage failure returns to the unprivileged Login panel. |
| Logging | Cause a denied catalog read, rejected input, successful product mutation, and confirmed purchase. Inspect the SQLite `logs` table. | Each event is timestamped; successful purchase audit and stock/history writes commit together. Authentication logs and Admin log-view access are verified with the integrated A/C providers. |
| Authentication and audit outage | Using temporary SQLite, sign in successfully and unsuccessfully, submit invalid login and registration input, then inject an audit-provider failure for a failed and successful login. | Auth, validation, and re-authentication events persist with timestamps and without credentials. An audit failure returns a generic error, creates no session, and rolls back attempt state. After the provider recovers, a normal sign-in succeeds. |
| Admin audit review | Sign in as Role 5, search by event and text, then attempt the same direct provider search as Client and without an access provider. | Only the current Admin receives read-only filtered results. Unauthorized attempts return no rows and create an `ACCESS_DENIED` event when storage is available; filters are treated as data. No operation clears stored audit rows. |
| Sensitive account audit outage | Inject failure for a `USER_ADMIN` audit event while changing an account role, then repeat with a working provider. | The failed attempt leaves the role unchanged and reports a generic error. Once persistence recovers, the role change and its audit row commit together. |
| Repeatable upgrade | Initialize the audit provider more than once over a database containing existing users and audit rows. | Existing users and audit history remain unchanged, with no log deletion. |
