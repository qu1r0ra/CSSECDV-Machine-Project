# Security documentation

Status: Bundle B implementation evidence for [issue #6](https://github.com/qu1r0ra/CSSECDV-Machine-Project/issues/6) and its approved implementation tickets [#7](https://github.com/qu1r0ra/CSSECDV-Machine-Project/issues/7) and [#8](https://github.com/qu1r0ra/CSSECDV-Machine-Project/issues/8). Service-level behavior checks use a temporary SQLite database. Integration with the actual Bundle A identity/session provider and Bundle C authorization provider, plus the live Swing walkthrough, remains pending under [integration issue #9](https://github.com/qu1r0ra/CSSECDV-Machine-Project/issues/9). These entries do not establish project-wide checklist compliance.

| Issue #6; checklist 2.2.2–2.2.3: Bundle B role authorization | [BundleBService.java](../app/src/Controller/BundleBService.java), [MgmtProduct.java](../app/src/View/MgmtProduct.java), [MgmtHistory.java](../app/src/View/MgmtHistory.java), role home panels | Role checks performed only in Swing could be bypassed through direct service calls. | A non-authorized account could change stock/prices, purchase inventory, or read another account's purchase history. | `BundleBService` checks the trusted current actor and authorization gateway on every operation, then enforces the B role matrix locally: Client/Staff/Manager catalog; Staff/Manager mutations; Client purchase and own history; Manager all history. Admin, Disabled, and absent actors are denied. UI controls use the same service permissions. `Main` currently injects a deny-all gateway until #9 supplies real A/C providers, so the standalone candidate fails closed. |
| Issue #6; checklist 2.1.10: fresh verification for catalog mutations | [BundleBService.java](../app/src/Controller/BundleBService.java), [MgmtProduct.java](../app/src/View/MgmtProduct.java) | A stolen or unattended authenticated session could perform high-impact catalog changes. | An attacker could alter prices/stock or delete products without proving current account control. | Add, edit, and delete each request a masked current-password entry. The gateway receives the actor, exact operation, target product, and request fingerprint. After verification the service rechecks authorization and confirms the same user, role, username, and session generation. Password `char[]` buffers are cleared in `finally`. The production gateway remains an integration dependency of #9. |
| Issue #6; checklist 2.3.1–2.3.4: strict B input and database handling | [BundleBService.java](../app/src/Controller/BundleBService.java), [BundleBServiceTest.java](../app/test/Controller/BundleBServiceTest.java) | Permissive parsing, floating-point money, or SQL string construction could accept malformed values or alter queries. | Invalid stock/price/quantity could corrupt inventory or purchase totals; crafted text could change database commands. | Names and history searches accept ASCII alphanumerics only (1–64 characters). Counts accept unsigned decimal digits and are bounded to 1–1,000,000 for purchase quantity and 0–1,000,000 for stock. Prices accept positive decimal values with at most two fractional digits and a maximum of 1,000,000.00. Invalid input is rejected without trimming, sanitizing, or rounding. Prices and totals use integer minor units and exact arithmetic. Runtime queries use `PreparedStatement`; DDL uses fixed statements. Legacy prices are migrated only when exactly representable to two decimals; otherwise they remain unavailable. |
| Issue #6; checklist 2.4.1–2.4.4: safe B failures | [BundleBService.java](../app/src/Controller/BundleBService.java), [Frame.java](../app/src/View/Frame.java), [MgmtProduct.java](../app/src/View/MgmtProduct.java), [MgmtHistory.java](../app/src/View/MgmtHistory.java) | Database/provider exceptions exposed to UI code could reveal implementation details or leave only part of a purchase committed. | Users could see internals, stock and history could disagree, or protected UI could remain visible after an unrecoverable error. | Service operations catch storage/provider failures and return fixed user-facing status messages. Product mutation, stock decrement, purchase snapshot, and audit write share a SQLite transaction; failures roll back. When storage remains available, the service attempts a timestamped failure outcome on a separate connection after rollback. That best-effort failure write cannot recursively retry itself. Provider/storage failures call `SecurityGateway.onUnrecoverableFailure()`, whose current frame adapter returns to Login. The actual identity provider must invalidate its session state when integrated in #9. |
| Issue #6; checklist 2.5.2 and 2.5.4: B validation and access audit | [BundleBService.java](../app/src/Controller/BundleBService.java), [BundleBServiceTest.java](../app/test/Controller/BundleBServiceTest.java) | Invalid fields and denied B operations could pass without a timestamped trace. | Repeated misuse or unauthorized B access could be harder to investigate. | Validation rejection, denied B operations, successful catalog changes, and confirmed purchases append timestamped events to the existing `logs` table using a `PreparedStatement`. Failed transactional outcomes are attempted after rollback. Current-password verification outcomes and authentication-attempt accounting remain owned by the A provider, avoiding duplicate B authentication events; Admin log viewing remains owned by the A/C integration and other bundle scope. Successful purchase audits are in the same transaction as stock/history writes. |
