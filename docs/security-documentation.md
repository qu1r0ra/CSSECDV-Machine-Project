# Security documentation

This document records the implementation and evidence for the integrated A/B/C candidate delivered for [issue #17](https://github.com/qu1r0ra/CSSECDV-Machine-Project/issues/17), following the assignment's required vulnerability, impact, and control format. The tested commands, remaining checklist gaps, and distribution evidence are in [TODO.md](TODO.md). Audit retention follows the settled #15/#16 rule: audit rows are append-only through application features, required audit writes fail closed, and there is no permanent audit-delete operation.

| Checklist 2.1.1–2.1.10: credentials and authentication (#9, #17) | [AuthService.java](../app/src/Controller/AuthService.java), [AccountStore.java](../app/src/Controller/AccountStore.java), [PasswordHasher.java](../app/src/Controller/PasswordHasher.java), [InputValidator.java](../app/src/Controller/InputValidator.java), [Login.java](../app/src/View/Login.java), [Register.java](../app/src/View/Register.java) | Weak or plaintext credential storage, distinguishable login errors, password observation, and repeated guessing could expose accounts. | Attackers could impersonate users, enumerate account names, or take over accounts through repeated guesses. | Passwords use PBKDF2-HMAC-SHA256 with 600,000 iterations, a random 128-bit salt, and a 256-bit derived key. Login performs a dummy hash for unknown usernames and shows the same generic invalid-credentials message. Registration requires 8–64 printable ASCII characters including upper, lower, digit, and symbol; usernames are 3–20 ASCII alphanumerics. Login and registration password fields are `JPasswordField`s. The fifth consecutive failed login changes the account to Role 1; successful login resets the counter. For a known username, empty, oversized, and otherwise malformed login passwords retain generic feedback, emit validation/authentication failure events without the submitted value, and count toward the same five-attempt lockout. Malformed current-password reauthentication by the active session emits both events and increments only the separate reauthentication-failure counter; it does not affect the login lockout. Attempt time/status is stored and reported after successful login. Audit and attempt state commit together; required audit failure rolls back and revokes the session safely. |
| Checklist 2.2.1–2.2.4: role authorization (#9, #17) | [AccessControl.java](../app/src/Controller/AccessControl.java), [Frame.java](../app/src/View/Frame.java), [BundleBService.java](../app/src/Controller/BundleBService.java), [UserAdminService.java](../app/src/Controller/UserAdminService.java), role home panels | UI-only checks or stale sessions could allow direct calls to protected operations or expose the wrong role home. | A user could change products, view other users' purchases, manage accounts, or read audit events outside their role. | `AccessControl` is the central role table and revalidates the active account/session for role homes and user administration. Business services also enforce their operation rules at each direct service boundary. Role 1, missing actors, stale sessions, and provider errors are denied. Swing acceptance verifies the visible home panel for each enabled role and verifies other role panels are not shown. The full feature matrix is in [access-control-matrix.md](access-control-matrix.md). |
| Checklist 2.3.1–2.3.4: strict validation and SQL handling (#9, #17) | [InputValidator.java](../app/src/Controller/InputValidator.java), [AccountStore.java](../app/src/Controller/AccountStore.java), [BundleBService.java](../app/src/Controller/BundleBService.java), [SqliteSecurityAudit.java](../app/src/Controller/SqliteSecurityAudit.java), [UserAdminService.java](../app/src/Controller/UserAdminService.java), [SQLite.java](../app/src/Controller/SQLite.java) | Permissive parsing, partial cleanup, unbounded text, or concatenated user values could corrupt data or alter SQL commands. | Malformed account/catalog/history inputs could bypass rules, corrupt business state, or expose/modify records through SQL injection. | Inputs are either accepted exactly or rejected; account, product, quantity, role, and search fields have strict character and length/range bounds. Prices use exact integer minor units. Runtime value-bearing SQL uses `PreparedStatement`; remaining compatibility `SQLite` surface delegates only to the parameterized, bounded audit search provider. Schema identifiers used in DDL come from fixed internal constants. Rejections do not partially mutate records and are audited where required. |
| Checklist 2.4.1–2.4.4: safe failures (#9, #17) | [AuthService.java](../app/src/Controller/AuthService.java), [BundleBService.java](../app/src/Controller/BundleBService.java), [UserAdminService.java](../app/src/Controller/UserAdminService.java), [Main.java](../app/src/Controller/Main.java), [Frame.java](../app/src/View/Frame.java), [History.java](../app/src/Model/History.java) | Database and provider exceptions could reach users, crash a protected workflow, or leave privileged state active after storage failure. | Internal implementation details could leak; business changes could become partial; a failed provider might leave a session or protected panel available. | Services return fixed user-facing outcomes and roll back failed transactions. Failed required audit writes roll back the associated authentication, user, product, or purchase change. A failed UserAdmin role-change audit ends the Admin session and invokes the configured safe-state listener; real SQLite audit-trigger failure tests also verify Bundle B rollback and fallback. Injected account-table failure verifies that session refresh revokes access and the user-management controller returns denial/empty outcomes. This is targeted failure evidence; checklist 2.4.3 remains open because it does not prove a universal crash boundary around every controller and database method. |
| Checklist 2.5.2–2.5.4: security-event audit (#9, #16, #17) | [SecurityAudit.java](../app/src/Controller/SecurityAudit.java), [SqliteSecurityAudit.java](../app/src/Controller/SqliteSecurityAudit.java), [AuthService.java](../app/src/Controller/AuthService.java), [BundleBService.java](../app/src/Controller/BundleBService.java), [AccessControl.java](../app/src/Controller/AccessControl.java) | Missing, mutable, or credential-bearing logs could prevent investigation of authentication abuse, invalid input, or privilege violations. | Security events could be lost, misleading, or expose submitted credentials. | SQLite audit writes use prepared inserts and UTC ISO-8601 timestamps. Authentication, re-authentication, validation, access denials, account administration, product changes, and purchase outcomes are recorded without submitted passwords. Required writes share the transaction with the protected change; failure blocks or rolls back the operation. Standalone audit schema initialization is additive and repeatable and does not remove existing rows. |
| Checklist 2.5.1: Admin account controls (#16, #17) | [UserAdminService.java](../app/src/Controller/UserAdminService.java), [MgmtUser.java](../app/src/View/MgmtUser.java), [AuthServiceTest.java](../app/test/Controller/AuthServiceTest.java) | Direct calls or weak reauthentication could let a non-Admin manage accounts or change protected account state without a durable record. | Accounts could be reassigned, disabled, deleted, or have credentials changed without authorization or an audit trail. | `UserAdminService` requires a current Role 5 actor for account listing, role changes, lock/unlock, deletion, and password changes. Sensitive role/delete/password operations reverify the Admin's current password and recheck the same session before mutation. The submitted password hashes are not shown in the user table. Mutations and `USER_ADMIN` audit events commit together; audit failure rolls back the change. |
| Checklist 2.5.1: restricted, non-destructive Admin audit review (#16, #17) | [SqliteSecurityAudit.java](../app/src/Controller/SqliteSecurityAudit.java), [MgmtLogs.java](../app/src/View/MgmtLogs.java), [SQLite.java](../app/src/Controller/SQLite.java), [AccessControl.java](../app/src/Controller/AccessControl.java) | A direct call or crafted filter could reveal audit events to a non-Admin or alter the query; a clear operation could destroy evidence. | Unauthorized users could read security history, or audit evidence could be permanently erased. | Each audit provider is bound by application initialization to the trusted `AuthService` using the same normalized database path. Search ignores the legacy caller-supplied `AccessControl` and checks the bound current Role 5 session, so an Admin session from another database cannot read these logs. Tests cover foreign-database denial and target-session authorization. Event and text filters are bounded and parameterized; results are read-only and newest-first. Admin can filter and show all records. No application operation permanently deletes audit rows; unauthorized searches are denied and logged when storage is available. |
