# Security documentation

Status: Bundle C (centralized authorization, admin management, logging, shared validation/error handling) recorded below. Bundle A (authentication) and Bundle B (products/purchases) rows are still pending from their owners.

Describe the vulnerability separately from its exploitation impact. Record the actual control, including its algorithms, parameters, and methods, after implementation.

| Security Requirement / Issue | Added / Modified File/s | Vulnerability | Impact | Security Control |
| --- | --- | --- | --- | --- |
| 2.2.1 Central authorization component | `Controller/Authorization.java`, `View/Frame.java` | No access check existed; any logged-in session could reach every role's panel. | A Client could open `AdminHome` and manage users/logs, or any role could view others' restricted panels. | Added `Authorization.check(User, resource, int... allowedRoles)`, a single method called before every panel switch in `Frame`. It denies on null user, disabled role (1), or role mismatch, and is the only path that gates `Content` card navigation. |
| 2.2.2 / 2.2.4 Role rules in logic and UI, strict home routing | `View/Frame.java` | All four role buttons (Admin/Manager/Staff/Client) were always visible and clickable regardless of the logged-in role. | A Client could click "Admin Home" directly from the nav bar. | `Frame.applyRoleVisibility()` shows only the nav button matching `currentUser.getRole()`; `Frame.showHomeForCurrentRole()` routes straight to that role's panel on login via `Frame.onLoginSuccess(User)`. Each button handler still re-checks `Authorization.check` as defense in depth. |
| 2.2.3 Authorization fails securely | `Controller/Authorization.java`, `View/Frame.java` | N/A previously (no authorization existed to fail). | An error or null session could default to granting access. | `Authorization.check` treats `null` user/roles and role 1 (disabled) as automatic denial before evaluating the allowed-role list; `Frame.currentUser` defaults to `null` (no access) until `onLoginSuccess` is called by the verified login flow. |
| 2.3.1 / 2.3.2 / 2.3.3 Reject-by-default input validation | `Controller/Validator.java`, `View/MgmtUser.java` | Role codes and passwords entered through admin dialogs were not validated before being persisted. | An out-of-range role value or policy-violating password could be written to the database. | `Validator` exposes boolean-only checks (`isValidRoleCode`, `isValidPassword`, `isValidUsername`, length/range helpers) that reject the entire input with no cleanup/sanitization, per the checklist's reject-by-default rule. Wired into `MgmtUser`'s edit-role and change-password actions. |
| 2.3.4 Parameterized queries | `Controller/SQLite.java` | Every method built SQL by string concatenation (e.g. `"...VALUES('" + username + "'...)"`), a direct SQL injection vector. | A crafted username/password such as `' OR '1'='1` could alter query logic or exfiltrate/corrupt data. | Rewrote every query and mutation in `SQLite.java` to use `PreparedStatement` with bound parameters; no SQL string is built from untrusted input anywhere in the file. |
| 2.4.1 / 2.4.2 / 2.4.3 Error handling | `Controller/SQLite.java` | Catch blocks printed raw exceptions (`System.out.print(ex)`) or silently swallowed them; callers had no safe-failure contract. | Stack traces could reach the console/log with internal schema and query detail; failures could leave UI state inconsistent. | Centralized every catch block through a private `SQLite.logError(operation, ex)`: UI/callers always get a safe default (`null`/`false`/empty list), the console only ever gets a generic message unless `DEBUG_MODE` is enabled (developer-only, still never surfaced to the UI). |
| 2.5.1 Admin-only log access | `View/Frame.java`, `View/AdminHome.java` | Reaching `MgmtLogs` depended only on UI navigation, not an access check. | Any authenticated session could reach `AdminHome`/`MgmtLogs` if the nav button were exposed. | `AdminHome` (which hosts `MgmtLogs`) is only reachable through `Frame.adminBtnActionPerformed`, which calls `Authorization.check(currentUser, "AdminHome", ROLE_ADMIN)`; no other code path shows that panel. |
| 2.5.2 / 2.5.4 Audit logging | `Controller/Authorization.java`, `Controller/SQLite.java`, `View/MgmtUser.java`, `View/MgmtLogs.java` | No audit trail existed for privilege violations or admin actions on accounts. | A compromised or disabled account's repeated access attempts, or an admin's role/password/lockout changes, would leave no forensic record. | `Authorization.check` writes an `ACCESS_DENIED` row (via `SQLite.addLogs`) on every denial. `MgmtUser`/`MgmtLogs` write `USER_ROLE_CHANGE`, `USER_DELETE`, `ACCOUNT_DISABLED`/`ACCOUNT_REENABLED`, `PASSWORD_RESET_BY_ADMIN`, and `LOGS_CLEARED` entries with the acting admin's username and a timestamp. |
| 1.1.2 (supporting) Admin account re-enabling | `View/MgmtUser.java`, `Controller/SQLite.java` | The LOCK/UNLOCK button only printed to console; disabled accounts had no working re-enable path. | A legitimately locked-out user would have no way back into the system even after in-person verification with the Admin. | `MgmtUser.lockBtnActionPerformed` toggles between role `1` (disabled, per [ADR 0001](adr/0001-account-disable-state.md)) and role `2` (re-enabled to Client) via `SQLite.updateUserRole`, logging the action either way. |
| 2.1.3 (supporting infrastructure) Salted password hashing | `Controller/PasswordUtil.java`, `View/MgmtUser.java` | Admin-driven password resets would otherwise store plaintext, and no shared hashing implementation existed for Bundle A's login/registration to reuse. | A database copy would directly expose every user's password. | `PasswordUtil.hash`/`verify` implement PBKDF2WithHmacSHA256 (120,000 iterations, 16-byte random salt, 256-bit key), storing `pbkdf2$<iterations>$<salt>$<hash>`. Used now by `MgmtUser`'s change-password action; intended as the shared implementation for Bundle A's registration/login. |
